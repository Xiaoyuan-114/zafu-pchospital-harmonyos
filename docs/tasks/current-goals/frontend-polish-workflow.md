## 1. 工作单元与推进规则

一个工作单元是一段可独立操作、可截图比较、可审查代码的用户流程，通常涉及 1–3 个主要页面。跨模块公共组件只修改本块所需部分，并记录受影响的页面。

每块按以下状态推进：

操作方式：用户指定使用命令行；模拟器通过 HDC/uitest 输入、布局检查与截图。禁止主动使用 Computer Use，确有必要时先向用户申请。

**确定范围 → 参考与改前截图 → 视觉/交互方案 → 实施 → HAP与模拟器验证 → 本地审查/修正 → 提交 PR 复审 → 修正审查问题 → 维护者决定合入。**

- 本地审查未通过：继续打磨本块，暂不推送完成版本。
- PR 出现阻断问题：优先修完本块，更新受影响的截图和验证记录，再提交复审。
- 等待审查时：可以盘点下一块、整理参考图和基线；保持下一块代码与当前 PR 分离。
- 维护者未合入时：按第 5 节处理分支依赖，不自行合并。
- 不按时间或提交数量宣布完成；以该块的页面效果和实际操作结果为准。

## 3. 每块的本地审查

本地审查包含界面审查、操作审查和代码审查。修完发现的问题后才能提交该块复审。

| 审查 | 做法 | 通过条件 |
| --- | --- | --- |
| 界面 | 对照参考图与同角色改前/改后截图；逐项看布局比例、字体/字重、图标、间距、图片、卡片与底部留白 | 事先列明的主要视觉差距已经处理；长文案和缺图布局完整，按钮/正文无遮挡 |
| 操作 | 安装本块 HAP，在模拟器按同一操作序列运行；检查返回、键盘、加载/空态/错误、重复点击与提交反馈 | 从入口走到真实结果，页面状态同步；失败后有可执行的恢复路径 |
| 代码 | 审阅本块最终 diff，沿调用链看身份/权限、状态/请求代次、幂等、路由和受影响公共组件 | 无阻断级缺陷；未破坏已有接口/权限与业务状态；改动范围与本块一致 |
| 证据 | 核对安装包、SHA/未提交差异、页面编号、截图、操作记录和未覆盖状态 | 每个改动页面有对应模拟器记录；参考/改前/改后与当前代码一致 |

本地问题分为：**必须修正、可保留差异、外部条件待解决**。必须修正项处理完再提交；可保留差异说明业务或参考依据；外部条件逐项写清所缺接口/环境和对流程的影响。没有完成关键流程的块继续标为进行中。

对于纯样式变化，用 HAP和模拟器核验；状态逻辑变化运行相关已有回归；接口变化检查真实返回与必要权限/状态；库存变化才增加对应最小数据库回归。保留 `backend-check`，不扩大为无关全仓测试。

## 4. 每块的交付包

每块目录形如 `docs/verification/frontend-polish-20261103/A-forum-feed/`，包含：

1. `README.md`：范围、页面/角色/入口、参考图、主要差距、最终修改、实际操作与结果、剩余问题。
2. 原始改前/改后与关键状态截图；按页面和状态命名，PR 中并列展示参考图、改前和改后。动态行为补操作序列或短录屏。
3. 构建/安装信息：代码 SHA及差异指纹、HAP SHA256、设备/系统/尺寸、主题/字体倍率、使用的 API 环境。包、凭据和本机签名材料不入库。
4. 本地审查记录：发现问题、修正结果及复核结论；检查使用「通过、失败、跳过、未跑」，未覆盖状态逐页记录。

PR 正文按本块实际交付重写，包含页面表、前后截图、关键交互、实际验证与剩余问题；不会只向尾部堆叠旧记录。代码提交与证据提交保持容易对应的关系。
